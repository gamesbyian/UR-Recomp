## Established paired observations

Original Snes9x and pinned native Switcher Race B both display MIKE **1:08.81** at absolute host frame **5783**. ## New optional original-only tooling

- tools/qa01_original_nmi_stack_pull_patch.py inserts a narrowly gated **read-only** architectural pull-scope logger around the single original Snes9x opcode dispatch. It requires the existing Switcher stack/NMI observer and full-accumulator PHA observer installed first into a **disposable** snes9x-libretro/cpuexec.cpp. It observes only PLA, PLX, PLY, PLD, PLB, PLP when their pre-opcode S and actual effective stack width imply reads touching 01DD or 01DE. **65C816 E mode overrides M/X for PLA, PLX and PLY**, so the observer now records a normalized `e0=0/1` flag as well as status bits (the actual pinned `CheckEmulation()` macro returns the `0x0100` flag value, not Boolean 1). PLD remains 16-bit. Each QANMIPULL row contains original CPU frame, V-counter, opcode PC, P/A, SP movement and pre-opcode bytes. The same gated opcode observer now also records candidate RTI scopes as QANMIRTI with handler PC, post-RTI guest PC/bank (strictly checked against stacked return when available), pre/post A/P/S, PPU V-counter and CPU cycles. The pre-RTI stack image also captures up to four guarded bytes (status, PC low/high, PB) so the actual stack-derived return target can be reconstructed independently when the entire image is in range. An RTI alone is not classified as an NMI: original IRQ/BRK exits can use the same instruction.
- tools/qa01_original_nmi_stack_pull_report.py validates the existing actual five-NMI/01DD-PHA source witness **before** accepting any QANMIPULL candidate. It enforces original CPU-frame 5778..5782, finite event budget, chronological order, **emulation-aware opcode width**, stack-pointer delta, and exact target-byte coverage. A PLA candidate must also restore the observed target byte(s) into the corresponding low/high accumulator position, preserving B on 8-bit PLA. It rejects malformed lines and returns 0/45 release credit. A zero-pull capture is a **bounded negative**, never a claim that no consumers exist.
- tests/unit/test_qa01_original_nmi_stack_pull.py supplies synthetic positive, zero and adversarial cases for pull and RTI, plus read-only/one-opcode-dispatch patch checks. **Synthetic fixtures are not source-executed evidence.**

The optional paired workflow additionally patches the **disposable pinned** `baldosa/snesrecomp/runner/src/cpu_state.c` using the existing `qa01_native_switcher_stack_gate.py` then `qa01_native_nmi_beam_patch.py`. On the **original Snes9x** side, the same one-opcode observer adds `QANMIPHABEAM` for the genuine `I_NMI+6 PHA`, retaining `CPU.Cycles` before/after, `ICPU.Frame`, `CPU.V_Counter`, original PC, A and stack. **Precision limit established by pinned generated source:** `gamesbyian/uniracers-recomp@10b864b.../src/gen/bank00_part00_v2.c` `I_NMI_M1X1` charges `cpu->master_cycles` for the entire `L_8588_M1X1` basic block **before** it executes PHB/PHD/PHX/PHY/PHA. Thus the native `QAcpu_master` observation at `PHA16` is already block-precharged, **not** a per-opcode/bus-cycle clock. The observer now also records `QAcpu_block_start` from the pinned emitter's `cpu->coprocessor_master_cycles` block-entry latch. **Further pinned source inspection found `cpu_write8_paced` and `cpu_write16_paced` increment `master_cycles` before each write callback**, including the observed PHA word write. Therefore `QAcpu_master` is the cumulative **post-pacing counter sampled at the write**, *not* the basic-block end. The monotonic pair `[QAcpu_block_start, QAcpu_master]` bounds numerical charged-counter accumulation but **does not bound an exact PHA instruction-cycle timestamp**. The reporter and crosswalk now use the correct `native_cpu_charged_counter_at_write` and `native_cpu_charged_delta_from_block_entry` semantics. Even an exact equality between `QAcpu_master` and some original Snes9x clock value would not demonstrate shared instruction timing. The native report and crosswalk now explicitly encode and require this caveat. Do not promote a raw horizontal-number difference to CPU cycle-parity evidence.

**Source-corrected RTI interpretation (2026-10-11):** The pinned Snes9x `third_party/src/snes9x-libretro/cpuops.cpp` `Op40Slow` restores P, PC and (in native mode) PB, and calls `CHECK_FOR_IRQ()` at the end. Crucially, the pinned `third_party/src/snes9x-libretro/cpuops.h` defines that macro as the **empty operation in both branches**. The earlier concern that this exact opcode may immediately chain an IRQ and thereby change post-opcode PC was not valid for this pinned core. When the four-byte stack image is in bounds, the parser now **requires** the restored address to match the post-RTI PC. Native-mode RTI consumes four stack bytes; emulation-mode RTI consumes three and retains prior PB. A missing in-bounds stack image prevents return-PC verification but does not prove a mismatch. A positive original RTI alone cannot identify NMI vs. IRQ/BRK ownership, match native CPU/beam phase, or certify a full event.

**Candidate saved-A consumer:** In the same 5778..5782 source trace, the analyzer separately reports whether a *later* 16-bit `PLA` exactly reverses the actual original `I_NMI+6` 01DD/01DE push (same CPU frame, S, word bytes and accumulator). **Chronology limit:** The report also records whether a source-observed original NMI PHA preceded the RTI within the same CPU frame.
