### Interpreter stack words are byte reads, not necessarily word-bus calls

Pinned Baldosa `runner/src/snes/interp816.c` implements `interp816_pullWord` by calling `interp816_pullByte` **twice**; `interp816_pullByte` increments the interpreter's own stack register and calls `interp816_read`. In `runner/src/snes/interp_bridge.c`, `bridge_bus_read` delegates each byte to the shared `cpu_read8` (and claimed word reads go via `cpu_read16`). Thus a real interpreter-executed 16-bit PLA *may appear as successive 8-bit bus reads* of `01DD=04`, `01DE=40`, rather than one 16-bit read of `01DD=4004`. The native journal and cross-report reconciliation now retain and independently derive both classifications. Adjacency means adjacency in the **filtered target-byte log only**, not consecutive physical bus accesses, not evidence that the interpreter executed a PLA, and not original/native timing parity. The `CpuState` S/M values collected by the shared bus logger are also **not proven identical to the interpreter's own in-flight S/M state**, so the AOT-style `S=read_start` heuristic is never required for this interpreter-shaped pair.
