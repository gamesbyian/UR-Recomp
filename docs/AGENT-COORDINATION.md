# Scheduled agents: shared-pool execution and recovery

**Current contract, 2026-10-26.** The five hourly agents are interchangeable workers, using the [single ranked board](HOURLY-AGENT-LINES.md). All five choose from the same top-five eligible jobs; **no per-agent anchors, fixed specialties, Agent 5 merge monopoly, Agent 4 Vault monopoly, or mandatory five new changes**. The historic specialized model survives in [the October 26 archive](archive/AGENT-COORDINATION-FIXED-ANCHORS-20261026.md). Actual concurrent edits and separation of independent QA from implementation still matter.

## Installed schedule and scope

Agent 1 starts at :00, 2 at :12, 3 at :24, 4 at :36, 5 at :48, hourly in America/Edmonton. These are staggered starts, not execution-duration caps. As of the October 26 2026 scheduler readback **all five were enabled and their prompts had been updated to the generic shared-pool contract**; preserve the installed staggered starts and validate live task state separately from this offline document. The `tools/agent_control.py --check` offline validator verifies the board minute contract and shared selection shape; it **cannot read the live scheduler**. A schedule check must explicitly inspect the actual five installed automations. No arbitrary change to minutes is required by this refactor.

Each invocation:
1. Read the fresh [AGENTS](../AGENTS.md), [work queue](WORK-QUEUE.md), this coordination policy, the [shared board](HOURLY-AGENT-LINES.md), current `main`, open/recent PRs/issues and directly relevant last handoffs. Inspect surviving Vault evidence **only as needed for candidate conflicts or recovery**. Do not reread entire historical source/vault by quota.
2. Assess **five highest-ranked eligible distinct jobs** or as many as exist. Inspect exact current PR/issue state, source or head, prior tests, dependencies and real concurrent edits for each; `hold`/`deferred` are not automatically implementation-ready. If a genuinely active writer occupies a target, choose another; an old branch/PR alone is not a reservation.
3. Pick the most valuable executable candidate, **currently favoring fresh-main incorporation of the open native title/root/controller work and qualification of the remaining held product fixes** above new research or infrastructure reports. Check whether candidate PRs have already merged before reserving a job. Advance it to meaningful closure or a precise external blocker, then pull the next candidate while useful work/time remain. Never force five new PRs/ZIPs just to meet a count.
4. Test cheaply and accurately. Source and executable identity belong in acceptance receipts. Reuse previous exact-head tests or build artifacts only when still applicable. Do not saturate the 20-runner budget or wait idle for GHA.
5. Publish reviewable source/tests promptly on GitHub (PR, issue, relevant specialist evidence); each handoff gives work ID, exact source/branch/PR, tests run/not run, what changed, independent reviewer if needed, reason for block and **the next discriminating action**. Merge qualified changes through required checks. A GitHub PR is an adequate handoff; **no routine second Drive journal**.
6. If a specific external prerequisite blocks the job (physical controller/audio/display, art acceptance, explicit platform refusal), leave an exact block and move on. Don't self-award release QA or source parity.

**Avoid source-collision CI churn:** Before publishing a competing implementation for a work ID, compare the live open PRs on that ID and their actual changed files and writers. Existing `python3 tools/ops_live_status.py --format markdown` now surfaces **recent same-work-ID PR overlap hints** from its already-fetched open-PR census, without extra API calls or CI jobs. The hints are strictly advisory: two disjoint test/implementation PRs may legitimately share a job, drafts and old PRs are not automatic source reservations, and a missing hint on an incomplete census proves nothing. Where genuinely overlapping, extend/review the existing head or choose the next eligible work ID rather than spending another 10–20-minute Windows job on a duplicate. Batch a coherent source/test change before each PR push when possible, but never suppress required checks or withhold useful integration solely to avoid CI.

A work-ID handoff belongs with the issue/PR and remains valid as the item moves in rank. A short continuation record is optional for otherwise unpublished work. The live board is the sole job assignment authority. An agent can review another's change and merge it if qualified, but cannot be both producer and independent accepting reviewer. Coordination uses exact conflicting file sets and active writes; do not place indefinite locks on a subsystem. Keep shared board/ledger edits serial or reconcile latest HEAD immediately before writing.

## Publication and owner risk priority

The owner explicitly accepts ROM and ROM-derived **public discoverability risks**, without asserting copyright or distribution rights; optimize the work for open, speedy, reproducible research. Do not add private storage, redaction, concealment, duplicate safe-substitute artifacts or slow approval layers merely because a ROM hash, extracted source-derived measurement or asset reference may be discoverable. Follow [owner direction](OWNER-ROM-RESEARCH-RISK-PRIORITY.md) and [first-party publication contract](recovery/FIRST-PARTY-PUBLICATION-CONTRACT.md). Genuine applicable platform/legal restrictions and explicit tool refusals remain controls, not invitations to obfuscate or evade them. Keep credentials, build integrity, source/asset identity, local user data and CI safe. Research visibility and release acceptance are separate concerns.

- Preserved source, GitHub-published source and merged main are distinct statuses. Use bounded source-epoch/member-integrity/dedup checks, not full old experiment requalification before publishing legitimate reviewable first-party source. Re-qualify changes for merge appropriately.
- When GitHub publication works, normal PR/issue/commit is the source of truth. Do not mirror or create redundant Vault receipts. On a real GitHub technical failure, retain exact source, patch, failure and source SHA; retry boundedly only when actually transient. On explicit policy/safety denial, never replay, disguise or route around it: preserve blocked material through authorized means, record exact refusal, seek authorized review and continue unrelated work. If the Vault itself is unavailable, preserve the complete artifact in another authorized handoff when possible, explicitly labeling what is at risk.
- A shared ranked work item for Vault integration is eligible for any agent. No agent automatically devotes every run to the Vault, and there is no separate compulsory recovery campaign if higher-value product changes are ready.

## Reporting / measurable outcomes

The next hourly invocation should leave at least one of: a qualified merge, a real product/source fix with test evidence, independently adjudicated release/event evidence, or a precise, actionable block. Report **ready-to-merge wait time**, count of qualified outstanding PRs, unique unpublished source, redundant CI builds avoided and finished player journeys when those measures are obtainable. Never infer 0/45 or 0/12 improvements from merged tooling. [RELEASE-QUALITY-LEDGER.json](RELEASE-QUALITY-LEDGER.json) alone owns release decisions.

Use `python3 tools/agent_control.py --check` after board changes. When new jobs are added, keep the rank contiguous, work IDs stable, status meaningful and a specific next executable outcome. Board rearrangements do not entail task prompt edits unless the common protocol changes.
