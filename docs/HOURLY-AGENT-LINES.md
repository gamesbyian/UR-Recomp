## Continue-until-exhausted execution policy (2026-10-19)

**A commit, completed investigation, submitted PR, CI launch, or status report is a checkpoint, never automatically a stopping condition.** After each milestone, complete source publication/receipts and exact-head validation before starting an unrelated item. While CI runs, inspect an independent next step from the second anchor, not three rotating support lines. If both anchors are blocked, record the exact barrier and preserve all source rather than generating another speculative handoff. The preferred outcome is less actionable backlog with one reviewable closure per invocation, subject to platform execution limits. **Do not fabricate activity merely to extend a run**, but do not declare completion simply because one small task succeeded. An hourly schedule defines invocation frequency, **not a promised 60-minute execution duration**.

Every final run report must identify: (1) primary anchor deliverable and exact closure status, plus any secondary fallback and reason; (2) commits, branches, PRs and exact HEADs; (3) tests actually executed and whether workflows were requested, running or avoided with reason; (4) remaining blockers, next discriminating steps and actionable handoff; (5) **the specific reason execution stopped**, distinguishing a real blocker, exhausted useful work, permission/tool failure, or platform execution boundary. Missing GitHub Actions runs alone are not a defect when existing authenticated evidence suffices. A blocked push is not a reason to stop if independent useful work remains.


## GitHub write-failure recovery (2026-10-19)

For a **plausibly transient** GitHub write failure (rate limit, temporary transport/provider safety rejection, or intermittent tool error), preserve the complete intended patch and source HEAD. **Wait four minutes and retry the write once** if the execution supports an actual delay and remains active. During the interval, independently advance another task rather than idle or babysit CI; do not mistake performing other work for an elapsed four minutes unless reliable timing is available. Immediately before retry, refetch branch HEAD/blob SHAs and rebase/reconcile if they have changed. After a second transient failure, preserve the patch and exact error in the PR/branch handoff if possible, or in the final report. If the platform cannot wait or execution ends before the interval, **never claim a retry occurred**; explicitly request a four-minute-delayed retry by a subsequent invocation or explain that the next scheduled run must pick it up.

Do **not** keep retrying permanent denials such as missing permissions, an explicit policy prohibition, invalid request validation, or a failed branch protection rule. Record the precise cause and use an authorized alternative. Do not work around access controls. Do not hold a session open solely to wait when further useful work is impossible.
