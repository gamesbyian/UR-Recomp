### What the existing USA fixture already settles

[The active-display note](oam-active-display.md) and [compatibility seams](emulator-compatibility-seams.md) document the canonical USA VS path: `tests/input/vs-first-race.input`, `tests/input/vs-first-race-observe.script`, the `tools/assert_uniracers_vs_oam_seam.py` assertion and `tools/decode_uniracers_oam_split.py`. A patched pinned Snes9x journal records HDMA `$2104 <- $A5` at line 0 and `$2104 <- $5A` at line 112 on five stable race checkpoints (guest 1140–1620). Channel 1, mode 0, reads `7E:206C = 70 A5 70 5A 00`. Captured end-frame high OAM `[0x218] = 0x5A`, whose four two-bit fields belong to sprites 96–99. The established top/bottom half expectation is an alternation of slots 98–99 and 96–97, as described by jgenesis.

**These are positive original-reference observations with bounded provenance.** They are *not* proof that a particular Baldosa/Modern frame composites those sprites, that its OAM snapshot reflects every live scanline, or that the current HD overlay's alpha mask/occlusion is correct. The current graphics owner additionally has newer same-day source/OAM/beam investigations; inspect **current merged main and those PRs** before proposing *any* new producer or rerunning this fixture. The source-backed `$0DDB=1` observation during actual 2P gameplay represents second-camera enable; it is not a failed split merely because a chosen flag is constant.

## 2. Net-new external comparison: another model, not another oracle

- **jgenesis:** [sprite engine at pinned revision `d19ee94f`](https://github.com/jsgroth/jgenesis/blob/d19ee94f64798946e30d8be7a3dc6f1f9f8732c8/backend/snes-core/src/ppu/sprites.rs) keeps `last_fetched_oam_idx` and uses it when the evaluated line has no sprites to fetch. Its [issue #164](https://github.com/jsgroth/jgenesis/issues/164) explicitly addresses Uniracers' HBlank split.
- **RustySNES:** [PPU specification at `98f8d398`](https://github.com/doublegate/RustySNES/blob/98f8d398020b8798b16076fae315960031c6b3b7/docs/ppu.md) describes an OAM evaluation-index redirect with a two-dots-per-entry model and a remapped high-table write (dossier C7.16), citing MesenCE. **Important limitation:** the documented implemented gate covers the evaluation phase, dots 0–255; it explicitly says the tile-fetch-phase index (dots 256+) is still awaiting an incremental range evaluator. jgenesis's cited Uniracers write is around H=282–284. The RustySNES evaluation-only arithmetic therefore **cannot be presumed to explain the Uniracers HBlank write** or be transplanted as a proven fix.
- **SnesLab:** [“Uniracers trick”](https://sneslab.net/wiki/Uniracers_trick) is the established scene label for writing OAM in HBlank without forced blank, with historical hardware-manual and NESdev pointers. Helpful vocabulary; no additional measured game state or new algorithm.

**Interpretation:** independent emulator projects supply useful *candidate mechanisms*, but ancestral reuse of MesenCE/bsnes/Snes9x assumptions prevents counting their identical effective address as independent hardware experiments. When the current graphics agent has a **real** native-versus-original visible mismatch, the smallest informative comparison is the source write's beam phase and effective target, line-specific OAM-high bytes **before and after the HDMA transfer**, actual evaluated/fetched slot, and the resulting **final visible** sprite pixels against original raw framebuffer/BG/OBJ priority. A constant end-frame `0x5A`, a rectangular slot or a decoded art tile alone does not identify the source of a displayed racer.
