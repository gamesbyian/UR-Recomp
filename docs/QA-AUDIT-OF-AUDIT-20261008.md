# QA-of-QA: completeness, economics and implementation audit

**Historical QA-of-QA critique, not an active implementation queue.** Its defect/evidence/feature taxonomy and resource stop rules remain valuable; the joint Baldosa/QA work now uses [WORK-QUEUE.md](WORK-QUEUE.md) and [QA-BOUNDED-RELEASE-CAMPAIGN.md](QA-BOUNDED-RELEASE-CAMPAIGN.md).

Status: **reviewed planning assessment; not release acceptance**. Review point: 2026-10-08 America/Edmonton / 2026-10-09 UTC. This audits the current `main` QA programme, issue inventory, the proposed 300-agent-hour campaign and the separate product plan. The canonical release gate states remain `RELEASE-QUALITY-LEDGER.json`. Future PRs may supersede the status here; do not quote this snapshot as a live CI report.

## Executive conclusion

**Keep all twelve QA risks, but change execution order.** The current programme is good at preventing false release claims and finding independent counterexamples. It is still vulnerable to a self-amplifying test infrastructure programme: work is indexed by QA number, multiple journeys duplicate evidence, no recorded time/throughput baseline supports an unconditional 300h completion prediction, and several release blockers are **unfinished features** rather than QA cases.

The **300 productive-agent-hour budget is a bounded discovery/repair tranche**, not an estimate or promise to finish all 45 USA courses, broad Remastered animation, full Modern menu implementation, physical hardware certification or every L4/L5 gate. It requires explicit checkpoint decisions before expenditure beyond the tranche. No fatal issue is waived simply because the budget expires.

Track **four ledgers separately**: (1) reproduced defect or source-proven concurrency bug; (2) release evidence gap; (3) functionality/design that has not been built; (4) accepted or optional limitation. A ticket should not move between categories because a test passed. Release-critical **missing functionality** must be assigned to its feature implementation owner, not allowed to disappear into QA-09.

## Proposed execution order (dependencies, not twelve parallel mini-projects)

**Stage 0: establish ground truth, cap ~10h inside the 300h pool.** Name one current main/candidate for measurement; inspect open #1043/#1045/#1052 (do not merge blindly); reproduce #890 on current shipped-keymap candidate or record nonreproduction. Create a single issue/witness index with existing source scripts and owners. Identify physical Windows tester(s) now. Do not freeze all development.

**Stage 1: stop genuine regressions and unblock journeys.** QA-02 live-fixture protection + packaged owner handoff; QA-05 Restart Return ownership; QA-08 no phantom racers and correct stock fallback. In parallel, run first genuine native/reference Race/Circuit/Stunt completions and wire the minimum visible Modern root. This stage supplies **new player outcomes**, not only more archaeological metrics.

**Stage 2: reuse four integrated scenario families.** 
1. Canonical authentic course completion + optional expert input and replay.
2. Two-pad tournament spanning leg 2/3, three entrants, relaunch, live-instance Busy/takeover, Records and selective storage faults.
3. Native moving 1P/2P/VS visual comparisons on 4:3/16:9 with stock fallback and exact source-OBJ priority.
4. Real Windows user session that crosses first-run menu, controls, pause, music/SFX, save/reload, reconnect and soak.
The storage cut experiments are **surgical fault variants of (2)**, not a fifth standalone product-flow duplicated from J-07/J-08.

**Stage 3: expand where the evidence is high-yield.** Generalize valid complete-event routes over 45 courses. Select pairwise/3-way combinations based on already failing interfaces, not all possible dimensions. Add expert/ghost/HD cases only when event families, camera classes or live framewise availability suggest risk. Request separate scope/budget for new art families, major interface build-out or system redesign.

## 100 / 200 / 300-hour checkpoint decision sheet

| Checkpoint | Required report (not assumed outcome) | Action on low yield |
| --- | --- | --- |
| 100h | Hours logged by output; defects fixed vs still open; named full-event completions by race/circuit/stunt family; #890/#1052/#1045 state; root menu true implementation status; Windows tester/accessibility availability | If no full-event completion, stop speculative course-reverse-engineering and fix input/terminal result **producer**; if no complete player route, shift from extra regression tooling to missing UI |
| 200h | 45 USA denominator: complete / partial / blocked / unverified; tournament multi-leg + 3+ status; cross-instance crash witness; native visible HD vs fallback counts; first exact candidate/hardware observations | Reallocate from low-yield investigations to one or two true blockers, or explicitly narrow private-playtest feature scope |
| 300h | Remaining confirmed P0/P1 defects; accepted limitations/feature exposure; required L4/L5 evidence still absent; actual agent-hour burn; separate feature/human/legal dependencies; revised residual risk and cost *range* | Stop automatic expenditure; request explicit new tranche with observed basis. No automatic release or gate waiver |

Each work item must have: `classification` (defect, evidence gap, feature, optional limitation); `player impact`; `first failing witness` or precise missing oracle; `lowest-cost next action`; `owner`; `dependency`; `scope/budget cap`; `stop condition`; `reuse IDs`; and `exact artifact` when applicable. Measure **productive** agent-hours consistently as active investigation+implementation+validation time; exclude queue wait, repeated failed CI caused by infrastructure, and idle agent wall-clock. Where those cannot be measured, mark the estimate uncertain rather than inventing productivity ratios.

## Do not mistake risk control for test completion

A failed QA gate is a release finding. A source-confirmed bug is already an engineering finding. A speculative risk is an investigation candidate. A missing screen is a product backlog item. They need different actions. A run may satisfy multiple QA properties **only when its logged observations actually include the independent required oracle for each property**.

The 300h budget does not authorize suppressing a known save-corruption bug, shipping broken advertised Remastered graphics, or labeling unverifiable races as passed. It **does** justify deferring optional art/catalog breadth, exhaustive PAL playback, redundant timing investigations and unjustified CI-matrix growth. The user-facing shipping configuration is an explicit product decision, not a hidden QA shortcut.
