### QA-02 implementation: tournament fixture double-publish race

Audit found a concrete time-of-check/time-of-use defect in `local_tournament_result_link_store.cpp`: `fs::exists` preflight was followed by replace-existing fixture publication, and the shared `.tmp` staging path allowed different processes to interfere. The fixture adapter now reserves unique `.pending-urfixture-*` staging directories and atomically **claims** the final fixture filename without replacement (Windows same-volume MoveFileExW without REPLACE_EXISTING, POSIX hard link). A second concurrent claimant returns Conflict without awarding points or overwriting the winner. The native test exercises an alternative valid pair, preservation of the incumbent bytes, ignored crash-orphan staging and eight competing writers expecting exactly one committed result. This closes the bounded **fixture receipt publication race**, not QA-02 overall: cross-file run/match/launch/profile transactional recovery, true power-loss durability, and packaged Windows multi-process acceptance remain open.

### QA-02 follow-up: mutable tournament staging and unresolved stale-retire race

Mutable `local_tournament_session_store.cpp` and `local_tournament_fixture_launch_store.cpp` also used shared `path + ".tmp"` before atomic last-writer-wins rename; concurrent processes could corrupt each other's staging bytes. The shared `local_tournament_atomic_replace.hpp` reserves distinct `.pending-urtournament-*` and `.pending-urlaunch-*` directories before complete write/flush/close, preserving whole-file replacement and old codec bytes. Unit stress: eight writers repeatedly replacing the same target, requiring one complete valid candidate and no completed staging residue. **This is not compare-and-swap**: independent process event-create or launch saves may still overwrite valid newer state. More critically, `retire_local_tournament_launch_file` still checks a pending attempt then removes the pathname nonatomically: source-confirmed stale-retire TOCTOU [#983](https://github.com/gamesbyian/UR-Recomp/issues/983). Treat this as a P0 QA-02 blocker for shared-user-root concurrency and fail-closed recovery, not solved by isolated staging.

### QA-02 launch-checkpoint stale-retire correction

The file-store TOCTOU in [#983](https://github.com/gamesbyian/UR-Recomp/issues/983) is addressed at the **local store** seam: checkpoint publication and exact-attempt retirement now take the same persistent, OS-handle-owned per-path `.urmutex` lock, enclosing the entire read/compare/remove critical section. POSIX uses `flock`, Windows uses `LockFileEx`; death of a process releases the OS lock without scavenging a PID sentinel. Unit test races 100 old-retire/new-save interleavings, with both possible orders always preserving the newer attempt and an explicit held-lock/release path. Isolated POSIX lock model passed 1,000 racing trials. **Do not mark QA-02 release accepted**: Windows packaged two-process, active event/session lost-update, power-loss and multi-file run/receipt/launch transaction remain open. Locking is cooperative and scoped to the canonical launch path.
