## Existing Baldosa staging pipeline: preserve, don't reintegrate

The source tree already has **20 project-owned `tools/baldosa_*` probe/adapter files** and dedicated workflows. Main's relevant merged path is:

1. `baldosa_guest_adapter_spike.py` wires `after_run_frame` into **our existing** racer state parser.
2. `baldosa_product_execution_spike.py` adds mapped *human*-word input only, retaining Ema's script/debug authority.
3. `baldosa_product_pause_spike.py` and existing native pause hooks add *acknowledged* frozen-guest lifecycle, not synthetic zero-input pause.
4. `baldosa_hd_host_spike.py`, `baldosa_single_presentation_scale_patch.py`, `baldosa_hd_enable_renderer.py` and `tools/baldosa_native_racer_presentation.cpp` expose our actual Remastered pixel presenter through the pinned framework raster.
5. `baldosa_ws24_host_spike.py` and `baldosa_ws24_framework_split_patch.py` bring our calibrated extra world tiles to both split bands; #1082 extends dimensions on these same APIs.
6. `baldosa_original_fallback_report.py`, `baldosa_ws24_presentation_report.py` and the existing native experiment workflow check real frame sizes, image changes, frame provenance and original-Baldosa CRC equality.

**Do not create a second runner, asset loader, world cache, pause callback, host-input filter or 4x Original fallback.** Avoid running parallel builds that individually compile the same 92 generated translation units if one pinned guest candidate could feed several independent acceptance slices. Existing plugin-style injectors are **disposable checkout staging**, not a replacement shipping executable yet.
