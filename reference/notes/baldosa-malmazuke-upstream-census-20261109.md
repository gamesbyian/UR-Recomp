## Exact-USA SRAM cross-reference: offset 0x10A7

**The shared menu-marker source behavior is now established in the pinned USA generated code; the observed one-byte divergence's cause and consequence remain unproven.**

- **USA UR original/native observation:** [UR original post-result byte witness](../../docs/QA01-ZOO-POSTRESULT-SRAM-ADDRESS-DISCRIMINATOR-20261015.md) independently replays the 2014 Zoom Zoo result. At +8/+16/+24/+32, original/native 8,192-byte SRAM agrees; at +64/+72 **only byte 0x10A7 differs** (original `0x0C`, native Baldosa `0x0D`). Two independently compiled original cores reproduce the observation, but no first writer/consumer or causal harmlessness is proven.
- **USA imported symbol:** `reference/imported/reverse-engineering/baldosa-uniracers-recomp/decomp/ram.txt` labels `77:10A7` as `sCutsceneTimer2`, a 2-byte league cutscene secondary counter. That is a descriptive Baldosa label, not independent USA dynamic source attribution.
- **PAL Malmazuke source research:** [R-0111](https://github.com/malmazuke/unirally-reconstruction/blob/19ecb59fb56bc9b3024a72ab9cba912586229769/docs/research/R-0111-save-image-exact.md) identifies `$10A7` as a **track-menu markers' step**, written by `$80:E872` and `$80:EB32`, and finds separate ending writes from `$83:B649`. PAL perturbation identifies `$10A7` as later readable in particular warm league/records routes; R-0111 still leaves seven ending-route value differences. Its initial version compared 916 of 919 native-run routes (3 rejected), not proof that all original-USA cases match.
- **New confirmed static correspondence from the original Baldosa USA source revision:** at [`decomp/symbols.txt`](https://github.com/baldosa/uniracers-recomp/blob/10b864b9d14a7b7416dd909eb7b054c88faef101/decomp/symbols.txt), `80:EB0D` is expressly named `Menu_CycleSpriteTiles` and described as stepping `77:10A7` from 13 through 0 while writing five menu sprites' OAM tile numbers. The pinned [generated USA guest translation](https://github.com/baldosa/uniracers-recomp/blob/10b864b9d14a7b7416dd909eb7b054c88faef101/src/gen/bank80_part0d_v2.c) actually reads `77:10A7`, decrements the word, resets negative values to 13, writes the result and later rereads it for tile selection; the same translation's `Menu_PickTrack` stores **zero** to the same 16-bit location before its menu animation. `recomp/symbols.toml` additionally registers the `80:E872` entry, matching Malmazuke's quoted PAL store site. These facts upgrade the earlier apparent *name-only* conflict to a **shared static menu-marker mechanism** in the pinned USA translation. They do **not** establish that the specific captured Zoo +32→+64 byte delta came from this writer or that later cutscene use is causally irrelevant. Baldosa's `sCutsceneTimer2` label is at least an incomplete description of this reused SRAM word.

**Testable source hypothesis:** the correctly seeded later case reproduces `0x0C` original versus `0x0D` native at result+64/+72. This is consistent with the menu-marker's 13→12 decrement having happened once on one side and not the other at the sampled frame. Verify which source PC was active, whether one extra/missing `80:EB0D` menu animation iteration explains the value, and whether later animation, result navigation or cold return consumes it. Do **not** promote consistency to causality, patch AOT arithmetic, suppress byte equality or rerun the already-completed six-sample census. The matching static method arose from a **shared original ROM source**, not two independent original captures.

**Remaining crosswalk work:** identify exact `83:B649` USA ending writes and any other readers in the current USA code, compare to PAL's ending/marker roles, then inspect current exact candidate's already retained result→menu phase witness. Only if those sources cannot distinguish the two update schedules should the owning QA01/CPU agent request one bounded original/native writer chronology run.

## Exact Git blob reconciliation: correcting the compare metadata

Both original Malmazuke revision trees were retrieved **without truncation** and compared by each file's Git blob SHA: **1006 old file blobs → 1081 new file blobs, 904 unchanged, 102 modified, 75 added, zero deleted**. The 177 individually indexed changed paths match this byte-level set exactly. Every entry now records its full **old blob SHA (or null if added), new blob SHA, size and change kind**.
