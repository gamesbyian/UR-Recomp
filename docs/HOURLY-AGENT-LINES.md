## The five-candidate selection loop

1. **Scan the top five eligible *distinct work IDs*** in descending priority. Read the latest relevant PR/issue, exact current branch/main, last handoff and any specific surviving Vault candidate. A five-job scan is a **decision set**, not five compulsory new implementations, ZIPs, PRs, or cursory reports. If the first five are blocked by genuinely concurrent writes or external acceptance dependencies, scan farther until five actionable choices are assessed or the list is exhausted.
2. **Prefer closure:** rank actual source-integrated user outcomes, finishing/reviewing an existing PR, unblocking the first independently accepted complete event, and fixing a reproduced release blocker above creating new analytical frameworks or experiments. An 'in_review' job may be selected for review, repair or integration; it is **not a license to edit another agent's active head**. `hold` requires the specified external prerequisite or a new independent fact; `deferred` is not selectable absent explicit reprioritization.
3. **Choose the most useful unblocked job**, using severity, release critical path, changed-user outcome, existing near-complete work, merge latency, duplicate effort and expected ability to complete a meaningful slice. Select a different job if the apparent owner is currently touching the same files. Do not infer an active reservation from a historic branch, issue mention, or old handoff. A single job can stay alive across many runs with one canonical receipt.
4. **Work, test, publish, hand off**: finish a source fix or completed integration when feasible; use narrowly relevant current-head checks and preserve artifact/source identities. Leave a PR/issue comment with what actually changed, exact SHA/checks, blocker/next step, owner of any independent verification, and release gate unchanged/changed with reference. Only append a short board-state update when the next worker's selection truly changes. No journal explosion or routine Drive mirror after successful GitHub publication.
5. **Continue while useful work exists:** after a real disposition, or a documented external block, advance the next eligible job, including when GHA runs. Never babysit CI or open speculative clones merely to consume the hour. If a task is waiting for human physical Windows/audio/art acceptance, identify the exact packet and move to another eligible job.
6. **Maintain review independence and merge hygiene:** do not self-certify original/native parity, physical Windows, art or release QA. Merge only qualified PRs after required checks, no forced source conflict overwrites. Preserve upstream intellectual-property/platform restrictions; do not invent extra secrecy controls. See [owner research risk direction](OWNER-ROM-RESEARCH-RISK-PRIORITY.md).

## Integration and risk principles

**One shared, finite queue.** There is no separate permanent integration, Vault, graphics, product, or QA scheduled-agent lane. Jobs remain free for any of the five agents except actual overlapping edits or separation-of-duties for approval. Multiple agents can each inspect a job, but duplicate implementation branches for the same discriminator require an explicit reason. The person merging a change may be any qualified agent; release QA verdicts still require distinct competent evidence review.

**Owner ROM risk priority:** The owner expressly accepts risks of public discoverability of ROM identities and derived research material, without claiming any publication or redistribution license. Optimize for speed, provenance and research visibility. Do not add secrecy/obscurity detours, unrelated security theatre, or mandatory private-storage steps solely to hide discoverable research. Preserve credentials, developer/user-data integrity, real rights/platform boundaries, and explicit refusal handling.

**Reality:** The last independently recorded ledger remains **0/12 accepted Windows release gates and 0/45 independently accepted full USA events**; update only from qualified independent evidence. Historic package and product progress scores are source-bound dated snapshots, not a status to force. At each run use actual current main and repository PR state; this board's October 26 pointers are initial orientation, never a license to describe stale statuses as live.
