# R4 contact-island extinction and reconstitution: bounded offline model

**Status 2026-10-11: *logical contact-cache experiment*, not running P2P multiplayer, not public discovery, not a real signature verifier, not NAT traversal or a release gate.** It complements the [self-sustaining P2P charter](SELF-SUSTAINING-P2P-MULTIPLAYER-RESEARCH.md), the [offline manual invite code laboratory](P2P-R2-R8-MANUAL-INVITE-OFFLINE-LAB-20261011.md), the [signature interoperability caution](P2P-R8-IDENTITY-SIGNATURE-INTEROPERABILITY-20261011.md) and the [R5 observation diagnostic policy](P2P-R5-OBSERVED-CONNECTION-DIAGNOSTICS-20261011.md). No project-operated bootstrap, permanent server, DNS, socket, external dependency, CI workflow, ROM or original guest changes.

Run: `python3 -m unittest tests.unit.test_p2p_peer_island_directory_v0 -v`.

The pure Python `tools/p2p/peer_island_directory_v0.py` models a bounded, per-installation directory holding owner-keyed candidate contact entries. These are **not** DHT entries, actual authenticated friends or automatically dialed sockets. It only accepts contacts when its caller asserts a verified **owner** signature from a separately audited future implementation. This module does not verify that claim; **the existing URP0 checksum is never adequate evidence**. Do not wire it to live incoming network packets without real standard Ed25519 verification, replay protection, recipient authorization and user consent.

## Frozen model boundary

- Each record contains a nonzero 32-byte key (hex representation), monotonic sequence, issue/expiry times (maximum 24 hours), up to four literal numeric IPv4/IPv6/port endpoints, scope `lan` or `wan`, and an explicit owner-issued `share_consent` flag. WAN-labelled endpoints must be globally routable IP literals; LAN candidates are never included in WAN introductions. No DNS or project URL resolution.
- At most 64 current contact entries per installation, at most eight contact introductions per explicit request. Capacity eviction is deterministic by earliest expiry, then issue time, then key; expiration is checked before export. Outbound introduction lists include **only** fresh owner-consented records in the correct scope. A node never implicitly shares private IPs to a public overlay.
- A higher verified owner sequence supersedes an older record. Same-sequence equivocation or stale replay is refused. A revocation is a newer owner-signed tombstone containing **no endpoints or sharing consent**; it suppresses replay of the older record until tombstone expiry. Durable revocation across offline intervals, identity rotation, signature verification and anti-eclipse resistance are **not solved** by this toy cache.
- A/B zero-cache cold start is represented by A sharing one externally verified address with B via a user-chosen channel. B may then offer A's own explicitly consented contact to C; C independently verifies A's signature before admitting it. Separate contact islands can be bridged by exchanging consented records without introducing an indispensable original bootstrap root. This is a model of information flow, **not proof of a usable network route or completed game**.
- Public discovery can improve typical convenience once independent peers are reachable. It does not solve the impossibility of finding an unknown machine with no shared contact, nor defeat hard NAT/CGNAT without willing reachable relays or explicit network configuration. Manual paste/share remains first-class and cannot be replaced by a mandatory project-controlled directory.

## Scope relative to the earlier R4 topology preflight

The earlier [R4 offline topology/reconstitution preflight](P2P-R4-EXTINCTION-OVERLAY-PREFLIGHT-20261011.md) tests zero-bootstrap network-island edges and explicitly injected routability, refusal and simulation mismatch. **This cache model does not replicate or replace that reachability simulator**; it isolates the owner-authorized *contact information* that may be introduced on those edges, with finite capacity, expiry, signature-witness assumptions and privacy gates. The [R5 observed stage diagnostics](P2P-R5-OBSERVED-CONNECTION-DIAGNOSTICS-20261011.md) separately handles truthful route-failure messages. Together they establish research policy cases, not actual sockets, RFC8032 signatures, global discovery, active netplay or acceptance of R4. Do not build three parallel runtimes from these experiments.

## Work needed before real networking

R1 deterministic cross-process guest simulation is an independent mandatory blocker. R2 must measure signed, consented manual routes with all bootstrap/DNS denied, including LAN/IPv6. R4 must then run **real isolated peer processes** with project endpoints terminated, fresh caches, manually imported signed contacts, churn, clock skew and cross-island introductions, inspecting packet captures and privacy. R5 must record actual direct/relay stage outcomes, not this model's candidate contact lists. R6 must enforce live session/recipient admission and per-peer quotas. Keep local 1P/2P and Records working fully offline throughout.
