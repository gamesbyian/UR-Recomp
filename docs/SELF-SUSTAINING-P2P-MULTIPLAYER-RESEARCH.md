# Self-sustaining decentralized online multiplayer: research charter and experiment plan

**Status (2026-10-11): future desktop feature; researched, not implemented or release-certified.** Online work remains deferred behind the integrated Windows Baldosa/Modern player journey and independent QA. This document owns the online-networking *research program* and its proposed end-state contract. The current schedule is owned exclusively by [WORK-QUEUE.md](WORK-QUEUE.md), the product boundary by [PROJECT-PLAN.md](PROJECT-PLAN.md), and actual acceptance by the relevant future release ledger entries. Do not start another full networking stack, background CI campaign, or macOS product port while the current Windows critical path remains open.

## Owner-set objective

Windows and macOS compatible UR-Recomp installations should be able to play authentic **two-player** Uniracers over the internet without anyone operating an indispensable service. The project may cease to exist: accounts, domains, source-hosting platform, developer, and all originally distributed bootstrap peers can disappear without making surviving copies inherently inoperable. Every installation is potentially a discovery participant; publicly reachable instances may *opt in* to rendezvous/relay work. No central authority, proprietary account, developer-exclusive keys, permanent required server, or runtime DRM/activation. Public discovery is permissionless, and compatible independent forks can interoperate on an open versioned protocol.

**Precise availability contract (no impossible promises):** Two compatible instances with an available direct network route (e.g. LAN, mutual IPv6 reachability, mapped public UDP/TCP endpoints) must be able to race even when *all project-controlled systems are gone*. If a route requires coordination or a relay, at least one reachable and willing intermediary must exist. A first-time isolated node must receive some initial contact information out of band or encounter a local peer; neither a DHT nor cryptography can conjure another machine's current address. The network can be **reconstituted** by users exchanging contact information; it cannot guarantee automatic global discovery from zero shared information. An exhausted entirely-offline network may restart as independent islands and reconnect when participants bridge them.

**No network requirement for local play.** Local 1P/2P, records and guest simulation remain wholly independent of network services. Networking is host-owned input delivery and session administration; never modify original guest physics, timing, scoring, RNG or progression. Keep original two-racer mode, rather than inventing additional guest racers.

## First-class direct invitations: play with specific people

**Product requirement:** automatic peer/lobby discovery is the normal happy path, but users must always be able to deliberately find **specific other people** by exchanging a copyable invite code, link or small portable connection descriptor *outside the game* (text message, email, Discord, QR, paper or any other medium). This is the recovery path when public discovery is unavailable, censored, partitioned, or simply fails. Invites are usable with **no developer website, URL shortener, identity provider, mandatory rendezvous server, or active global DHT**. Exchanging invites must never require telling strangers a password or private identity key.

**Preferred user experience:** `Multiplayer → Play with Friends → Create Invite` produces a human-shareable code plus a deep link (`ur-recomp://join/<encoded-invite>`, final scheme/name to be standardized). `Join with Code` accepts both a pasted code and complete link regardless of OS/deep-link handler registration. Receiving a link may launch an installed app where supported, but clipboard/paste and file import are mandatory fallbacks. Invite owners can copy a replacement/refresh when their reachable addresses change; UI distinguishes expired, superseded, unreachable and incompatible invitations. Confirmation displays host identity/fingerprint and expected racer/session before consent to connect. Users may specify a **particular recipient** by out-of-band verified public key/fingerprint so only that recipient can use a restricted invite.

**The invite is a typed, open, versioned, self-contained descriptor, not a URL requiring an API lookup**: proposal fields are protocol version, lobby/session nonce, inviter public key/fingerprint, supported guest-simulation compatibility identity, short validity window, connectivity candidates (IPv4/IPv6 and ports, with hostname only as an *optional* hint), optional signed independently operated rendezvous/relay hints and a signature/authentication tag. Private invitations additionally bind a recipient key or carry an unguessable short-lived join capability. Define canonical serialization, checksum/typo detection, strict length bounds and deterministic encoding. Don't place the private key, account tokens, permanent personal information or undisclosed local addresses in a shareable invite. Public endpoint exposure is an informed-consent/privacy choice; short user-friendly codes **cannot** resolve arbitrary dynamic endpoints offline without an existing peer directory or other out-of-band information. Therefore support a longer portable self-contained payload and an optional compact alias only when the alias can actually be resolved through available peers.

**One-way vs two-way exchange:** a single invite may suffice when the inviter is directly reachable or a consenting rendezvous/relay peer is already reachable. With both users behind restrictive NAT and no reachable intermediary, the product offers an explicit `Reply with Connection Code` / `Import Reply` exchange carrying fresh ICE candidates and credentials or compatible signed negotiation material. Both clients try authorized simultaneous connection attempts with bounded timeouts. Exchanging SDP/ICE candidates or cryptographic metadata cannot *guarantee* connectivity across arbitrary NAT/firewall combinations: when an independent intermediary or manual port-forward is required and missing, explain the limitation honestly instead of showing an endless spinner.

**Two or more friends:** a shareable *group invitation* may introduce several peers and advertise an opt-in waiting room with a signed membership roster and host-selected two active racers. Original game simulation stays strictly two-player. Extra participants can wait, chat or spectate only if those separate features are eventually implemented; neither multiplayer networking nor this research charter silently commits to chat/spectator functionality. Different peers may exchange signed contact descriptors directly to reconstruct discovery islands; never implicitly reveal members' network addresses to all invitees without consent. Per-invite admission limits, expiry, cancellation, join approvals, replay resistance and duplicate-join handling apply.

**Research additions:**
- R2 must prove paste/import invite joining works while *all* discovery and DNS traffic is blocked, both on isolated LAN and across manually routable endpoints.
- R4 must prove two brand-new installations with **no previously shared network roots** exchange descriptors over an external messenger, start a two-node overlay, and share a fresh group invitation with a third peer.
- R5 must compare one-way, two-way exchanged-candidate, volunteer-relay, and impossible-to-connect NAT configurations, with user-facing truthful diagnostics.
- R6/R9 must fuzz malformed/deceptive/oversized links, expiry and invite replay, signed binding, restricted recipients, sensitive endpoint exposure, copy/paste/URL-handler safety and cancellation.
- R8 must include code/link canonical test vectors and independent-client parsing/conformance, including clipboard/manual entry and no-resolution-required cases.

**Acceptance:** A and B can agree to race through an invitation shared outside the game when global discovery is dead, and the game never attempts a proprietary lookup. A can invite B and C into a group for scheduling/direct discovery without inventing a third simultaneous original racer. When neither A nor B is reachable and no usable relay/route exists, a clear diagnostic and a feasible remedy (port mapping, reachable peer relay, or network change) replaces a false guarantee.

## Architecture hypothesis, explicitly provisional

Separate four independent seams so a better transport or discovery design can be substituted without altering gameplay:

1. **Identity / trust:** locally generated long-term public key, portable fingerprint and revocable/rotatable local identity. Never rely on a hosted account, certificate authority, or project-controlled key. Bind offers and session handshakes to signatures, randomness and a short expiry. A connection invite includes fingerprint verification material; never implicitly trust arbitrary text from DHT. Keep optional local friends/blocked peers in host storage.
2. **Discovery / cold start:** LAN multicast, manual address and signed invitations as mandatory fallbacks. Maintain bounded, freshness-ranked peer cache and support manually imported/exported peer-contact bundles. A small independent overlay can use DHT lookup of signed, expiring lobby records; PEX or bounded gossip helps an established peer introduce others. No privileged bootstrap keys. Shipped example peer addresses may accelerate entry but must be removable and **must not be required**. Headless community nodes use the same open protocol, not a special privileged daemon. Optional external networks may be examined as *non-essential* discovery paths, with privacy and namespace pollution assessed.
3. **Connectivity / transport:** opportunistically connect by routable IPv4/IPv6, then eligible router mapping / ICE hole punching; employ a bounded opt-in volunteer relay if direct routes fail. Prefer a direct, low-latency session route. Relay selection and reservation are peer-negotiated; no vendor-owned signalling or STUN/TURN endpoints in the mandatory path. Router port mapping must be user-controllable. Connection diagnostics must distinguish no peers, NAT obstruction, privacy settings and incompatible build.
4. **Guest input / session synchronization:** only session-negotiated controller words and protocol metadata enter the guest input seam at the same original fixed tick rate. The full original native 2P guest is the single gameplay authority on each participating machine; neither peer supplies remote position/physics hacks. First prove delay-based frame lockstep under controlled jitter, then investigate bounded rollback if complete state restoration is proven. Negotiation pins exact canonical ROM/core/guest simulation and input mapping compatibility separately from optional presentation differences.

Never route high-rate frame inputs through DHT lookups. A DHT carries discovery and small signalling data, not race traffic. Never write open-lobby advertisements to an existing public network without evaluating its protocol, abuse, and privacy implications.

### Candidate evaluation tracks, not commitments

A. **Native-first mix:** OpenDHT for lobby routing and peer discovery + standalone GameNetworkingSockets for authenticated P2P transport using a UR-defined signalling adapter. Test volunteer relay capability separately; combining libraries does not make that work automatic.

B. **Unified protocol:** libp2p (likely Rust via a narrow C ABI; evaluate C++ against the exact DCUtR/relay-v2 feature matrix) for DHT, secure links, relay reservations and hole punching. Determine whether its QUIC/stream semantics meet 60 Hz input-latency needs.

C. **Jami-derived integrated reference:** DHTNet for a spike only; assess GPL-3.0 and transitive licences, PJProject fork, cross-platform build and maintained relay policy before considering shipping.

D. **Minimal connectivity control:** libjuice or libdatachannel + a deliberately small bespoke discovery overlay. This saves framework bulk but incurs security/protocol maintenance; acceptable only if measured simplicity offsets the risk.

Selection rubric: no developer-controlled runtime dependencies (hard gate), recovery after network extinction (hard gate), independently implementable published wire format (hard gate), Windows/macOS support, High Sierra as best effort, all-connection failure transparency, licensing/reproducible vendoring, memory/CPU idle budget, relay cost and consent, latency/jitter, NAT matrix coverage, maintainer burden. **No production dependency selected by this survey.** Third-party code intake requires [TRUSTED-UPSTREAM-ADOPTION.md](TRUSTED-UPSTREAM-ADOPTION.md), [THIRD-PARTY-CODE-AUDIT.md](THIRD-PARTY-CODE-AUDIT.md) and [TOOLCHAIN.md](TOOLCHAIN.md).

## Program: bounded experiments and falsifiable exit criteria

The research questions below are sequenced; **do not treat them as current P0 tasks**. Each spike should produce a small test script/spec, pinned library revision and licences, command line, reproducible environment, results and a negative/failure witness. Run offline/in a sandbox before opening firewall ports or contacting public peers.

| ID | Question / experiment | Evidence and exit condition |
| --- | --- | --- |
| R0: architecture inventory | What exact 2P input ownership, guest frame cadence, pause/restart, SRAM, RNG, state snapshot and presentation/audio side effects currently exist in merged Baldosa/Modern? | Contract inventory referencing tested source, not a duplicate execution engine; track missing deterministic snapshot/restore seams. |
| R1: deterministic two-process race | Can **independent processes** consuming the same initial guest state and exact input frames finish Race/Circuit/Stunt with equal full authoritative state at every checkpoint? | Frame-indexed hashes, full guest-side source state where necessary, desync minimizer, 1P/2P tests. Separately repeat Windows-vs-macOS once a macOS backend exists. Compare complete reproducible events, not only a WRAM subset. |
| R2: isolated cold-start LAN | Can two previously unknown installations (including disconnected LAN) discover/connect and complete a race without DNS, public bootstrap peers or internet? | Packet captures / dependency-denial logs; multicast plus manual-IP fallback; no third-party requests, no surprise background services. |
| R3: library bake-off | Which candidate connects native Windows/Windows and Windows/macOS peers with least dependency and lowest 60 Hz latency? | Same packet grammar and workload through candidates A/B/C/D where feasible; build pin, SDK/licence audit, binary sizes, CPU, idle network, RTT/jitter/loss under control. Explicitly test public IP, NAT, IPv6-only cases. |
| R4: extinction and resurrection | Can peer A and B erase all cached/bootstrap nodes, exchange one signed manual invitation or an address, start a new overlay, accept peer C, and interconnect isolated islands later? | Automated shutdown of *every* original bootstrap/discovery/relay fixture; fresh-install cold starts, offline LAN, manual WAN and cross-network bridge. Failure must distinguish no route from no discoverability. |
| R5: NAT/relay adversarial matrix | What percent of attempted connections complete under tested combinations of public IPv4/IPv6, typical home NAT, endpoint-dependent mapping, CGNAT, restrictive firewall, IPv4-only/IPv6-only and both blocked? | Per-stage result (peer discovery → reachability → relay reservation → hole punch → gameplay), direct vs relayed RTT and bytes. **Never** compare unconditional game-success to 2026 paper's conditional 70% statistic. Verify volunteer bandwidth/connection/time caps and opt-out. |
| R6: lobby correctness and hostile discovery | Do signed time-limited offers survive churn, spoofing, out-of-order updates, malformed packets, stale identities, unwanted unsolicited joins and Sybil/eclipse pressure? | Fuzz/unit/integration fixtures: TTL bounds, replay resistance, public key verification, lookup path diversity, quota and rate limits. No centrally issued identity or single global lobby writer. |
| R7: lockstep → rollback | Which delay budget is playable and what state is actually safe to serialize/restore? | Deterministic lockstep race with packet loss/jitter/reordering/disconnect; then only if bounded snapshots/resimulation passes, GGPO-compatible or custom audited rollback trial. Prevent duplicated audio, storage writes, visual effects and results during replayed frames. |
| R8: protocol permanence | Can an independent minimally implemented peer (not the original executable) establish identity, advertise lobby, negotiate version, exchange frames and refuse incompatible simulation cleanly? | Published wire-format fixtures, version/capability matrix, cross-client interoperability test, migration/deprecation rule, test vectors and protocol conformance README. |
| R9: user/privacy/safety | Can multiplayer be disabled fully and relaying opted into without exposing users unexpectedly? | UI test for opt-in traffic, local-only mode, relay caps, IP disclosure warning, blocking, restricted keys, invalid/fuzzed packets, credentials backup and rotation; check that offline records never depend on availability. |

### Connectivity matrix minimum

LAN same-subnet, LAN AP isolation, IPv4 public/public, public/NAT, NAT/NAT, restrictive NAT/NAT, CGNAT/CGNAT, IPv6 global/global, IPv6-only/IPv4-only, Windows/Windows, Windows/macOS, peer quit mid-race, relay quit mid-race, reboot with no known peers, network partition and reunion. For every case report *direct*, *volunteer-relayed*, *manual port mapping required* or *unavailable*, not a deceptively successful “connected” boolean.

### Security, identity, records and cost boundaries

- **Peer keys are locally generated** and permit pseudonymous identities; no guarantee of anonymity when exchanging public-IP candidates. A malicious discovery peer can observe request metadata and a malicious lobby member may discover the other's IP.
- **Relay participation is explicit opt-in**, with data/time/concurrency ceilings and simple shutdown. Every player can *participate* in discovery without consenting to forward arbitrary strangers' internet traffic. The network tolerates zero relay volunteers but cannot promise all NAT combinations then.
- **No globally trusted leaderboard.** A signed self-reported race is attributable but not automatically fair. Existing .urrun/.urmatch host-owned publication and terminal provenance stay authoritative for local evidence; peer attestations and anti-cheat claims are separate later research and must not contaminate local PB semantics. Host roles cannot introduce a second simulation.
- **Abuse resistance** includes key/address replay rejection, source and subnet diversity, small signed records, per-identity and per-address quotas, rate limiting, bounded clocks and deserialization, authenticated encrypted session channel, offline fuzzing and handshake timeouts. Signed advertisements alone do not prevent a network eclipse.
- **Preservation** includes minimal mandatory cryptographic primitives, open licence/implementations and downloadable protocol tests with no domain dependence. Source code availability alone is not enough if binaries require a remote API to start.

## Proposed functional acceptance (future, not today's QA ledger)

1. Offline local gameplay unchanged.
2. Two independent Windows copies race on LAN with DNS and public internet denied.
3. Two routable Internet peers race via a manually shared connection description with all developer-operated infrastructure absent.
4. Network is deliberately emptied; two users establish a new overlay without consulting any historical canonical bootstrap host and admit a third, with an honest explanation when manual reachability is unavailable.
5. Independent headless node and at least one independent client implementation can interoperate, with no developer signing key or account.
6. Compatible Windows/macOS guest runs have identical authoritative checkpoints and settled original rules; presentation options do not alter simulation.
7. Constrained NAT failure shows meaningful remedy or opt-in volunteer relay, never silently falls back to a proprietary service.
8. Security, replay integrity, privacy and dependency/rights checks have passed a separately owned adversarial acceptance campaign.
