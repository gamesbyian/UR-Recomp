# Local Tournament launch checkpoint: atomic host-store seam

Status: **standalone storage utility and strict C++17 tests; not wired to Windows product routing.** This slice depends on the pure launch/restore contract in `MODERN-LOCAL-TOURNAMENT-LAUNCH.md`.

The future live tournament host must save an attempt-scoped launch checkpoint **before** entering the original guest 2P route. The checkpoint's exact canonical `UR-LOCAL-TOURNAMENT-LAUNCH/1` bytes contain the active tournament ID, live attempt ID, selected fixture index/round/course/profile identities and the full immutable roster/schedule digest. The checksum detects accidental corruption; it is **not** an authorization signature.

`native/product/local_tournament_fixture_launch_store.{hpp,cpp}` reuses the repository's existing host state persistence pattern:

- One explicit host-provided path under an existing per-user data root. This layer does not choose a filesystem location, create an independent root or scan saved match history.
- Validate/encode first, then write a same-directory `.tmp`, check complete write/flush/close and atomically replace the destination. Windows uses `MoveFileExA` with replace/write-through flags; other hosts use `rename`. A rejected candidate never overwrites the prior checkpoint.
- Read a maximum of **2,048 bytes** and distinguish missing, rejected/corrupt and I/O-error status. Decode must be canonical and the embedded tournament ID, selected unfinished fixture, participant identities and full schedule fingerprint must match the current authoritative tournament state before returning a pending attempt.
- Idempotent explicit retirement through the owning lifecycle, **only for the exact previously published checkpoint**, even after the fixture becomes completed. This deliberately differs from *restore*, which only admits unfinished fixtures. A stale cancellation cannot remove a newer attempt at the same path, and corrupt files cannot be silently retired as though they were an authorized launch. No result is generated by loading or deleting a checkpoint.

The caller must serialize writes to one checkpoint path, choose the existing account/profile-specific root, mint the instance/attempt IDs securely and transactionally coordinate checkpoint publication, actual stock route entry, completed paired run+match commit and fixture receipt persistence. A standalone successful save is **not** proof that a guest race occurred or that a tournament is playable. Process restore of an unfinished guest race is not claimed; a host that cannot safely resume it must explicitly cancel/retire the attempt.

Strict test coverage uses a real temporary filesystem: save → verify exact bytes → fresh-load, wrong instance/other entrant/other fixture/finished fixture rejections, invalid replacement preserving previous bytes, corrupt/truncated/oversized containment, repair, empty paths, missing directory, and clean idempotent retirement. It runs within the existing focused local-multiplayer contract workflow and tooling-unit suite. No new heavyweight native-boot workflow is introduced.
