# First-party Vault-to-GitHub publication contract

Owner direction, 2026-10-22. Applies to manual end-to-end recovery sessions and the five scheduled agents when they encounter preserved first-party source. This is a **publication** policy, not an exemption from branch protection, ROM/rights boundaries, independent QA or release gates. The live [shared ranked assignment board](../HOURLY-AGENT-LINES.md) applies equally to all five interchangeable scheduled agents. The owner's [ROM research-access policy](../OWNER-ROM-RESEARCH-RISK-PRIORITY.md) rejects secrecy-driven friction based only on discoverability.

## The default presumption

The restricted recovery Vault holds **our own commissioned agents' work**, often already tested to the project's specifications. Presume it deserves timely recovery, not a full new scientific investigation simply because transport via GitHub originally failed. Historical test reports are genuine evidence of what was previously run, but not proof of a new run or of unchanged main compatibility.

1. **Preserved** means complete bytes and provenance survive in the restricted Vault.
2. **Published** means legitimate source, tests and limitations are accessible on a GitHub branch or PR, including a clearly labeled **draft** when unfinished.
3. **Integrated** means an appropriately reviewed, qualified change has merged into `main`.

Do not treat these as interchangeable. **Get useful work to GitHub first; qualify for merging second.** No blanket requirement to rerun archived experiments, prove historical conclusions from scratch or receive full native/release approval merely to open a reviewable draft PR.

## Minimal prepublication checks

- Confirm actual source/member integrity, real rights/platform constraints and credential/user-data safety. The owner's acceptance of public ROM/derived-data discoverability risk means research must not be delayed by speculative secrecy controls; it grants no redistribution license or right to bypass an explicit platform refusal.
- Identify source revision, changed files, existing tests, and whether the same work already exists in `main` or an accessible PR. Perform a bounded current-head comparison.
- Prefer publishing original source/test bytes with provenance and stated limitations. Make necessary conflict fixes only, not a speculative rewrite. Keep one small PR per coherent reusable implementation.
- When code still conflicts, publish the intact non-prohibited original material on a clearly named recovery branch/draft PR as appropriate, rather than waiting for an unrelated acceptance campaign; clearly mark integration work outstanding. Never force a broken branch into `main`.
- If the source is already fully present, record a concise semantic-supersession disposition. Historical research-only material can move to Evidence after verified readback; don't equate folder moves with source integration.

## After GitHub publication

Run the **normal** repository merge checks and source-appropriate tests. Reuse exact-source prior evidence when applicable; run additional work for actual code changes, changed preimages, absent or conflicting evidence, and required independent review. Normal PR CI is preferred. **No CI quota** or invented manual dispatch requirement, and never wait idle for a runner while another disjoint recovery candidate is ready. Follow actual branch protection and specialist acceptance authorities. Do not self-approve original/native, Windows physical, art/character, ROM/rights or release gates.

## Recurrent connector refusals are unresolved publication defects

A rejected invocation alone does **not** establish that the first-party source is improper or permanently ineligible. Capture raw error, exact operation, path, blob/preimage SHA and complete source/test package. Explicit safety-restricted invocations must not be replayed, cosmetically altered or routed around a control to get past it. Seek **authorized confirmation or review** of suspected false positives; independently reconcile source against recent merges and pursue substantively distinct legitimate engineering changes through regular permitted review. Technical errors (timeouts, 429, 5xx, stale preimages) warrant bounded source-aware retries. Never relabel an explicit refusal as a transport exception. Preserve blocked original bytes in restricted Drive with independent download/readback, and keep a concrete recovery next step; a denial must not terminate unrelated work or become a permanent feature veto.

## Division of labor and accounting

One **end-to-end manual recovery agent** owns scout → branch/draft PR → source adaptation → relevant CI → merge/disposition. Do not create a new team or approval queue. Five hourly agents now select from one shared pool, including relevant Vault integration jobs; there is no assigned recovery agent or exclusive merge writer. A manual integrator may also advance stranded packages without duplicating genuinely active writes. Ownership is per **specific active branch/file/candidate**, not inferred from an old PR.

Prefer useful source publication over administrative cleanup. Use existing PRs, #2088 and minimal work-ID pointers rather than growing shadow ledgers. Report **new GitHub publications, merges, substantive capability, honest checks and remaining unpublished source** separately from Evidence moves and already-merged duplicates. Existing vault files and intentional owner deletions remain untouched absent specific disposition.
