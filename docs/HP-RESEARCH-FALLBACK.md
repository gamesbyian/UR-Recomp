# Owner HP missed-schedule research fallback (opt-in)

**Problem, November 1 2026 UTC:** GitHub's normal `schedule` delivery for the HP hourly research workflow has not been reliably observed since October 31 21:36 UTC. An eight-worker `workflow_dispatch` run completed successfully, so the runner and research code are known to work when GitHub *does* dispatch. GitHub cron is retained, not duplicated or disabled.

## Install (owner action only)

On the owner's **Windows x64 HP PC**, use the four-file ZIP containing `Install-HP-Research-Fallback.cmd`, `Install-HP-Research-Fallback.ps1`, `hp_research_fallback.py` and `Uninstall-HP-Research-Fallback.cmd`. Extract the ZIP to a normal local directory, then **double-click `Install-HP-Research-Fallback.cmd`**. This checks `py.exe` (Python 3) and `gh.exe` with an existing authenticated GitHub login; it never downloads a dependency, asks for a new GitHub token, uploads files or dispatches an initial run. If a prerequisite is missing, the installer reports an error rather than weakening the model.

The installed Windows Task Scheduler task runs under **the owner's current logged-in user** every 15 minutes. This choice avoids a stored Windows password and shares the already-authenticated `gh` credential store. A locked screen is fine; a fully logged-out session is **not** supported. The task never grants elevated rights and never executes repository code locally. Remove the task by double-clicking `Uninstall-HP-Research-Fallback.cmd`, or through Task Scheduler. The local script and last diagnostic remain under `%LOCALAPPDATA%\UR-Recomp\HPResearchFallback`; deleting them is optional after uninstall. Installing a newer package replaces the same named task, not a second timer.

## Dispatch algorithm

Each check uses `gh api` to read **the latest 30 runs for the specific research workflow**, the two other owner HP workflows, and exact current `main` SHA. It refuses to dispatch when: any research run is queued/active; an owner HP main build or benchmark is queued/active; latest research run started less than **90 minutes** ago (manual or schedule); latest run failed/cancelled on the **same main SHA** (stop retrying an unresolved source defect); the API response is missing/malformed/unauthorized; or a second process already holds the local lock. It performs a second research census immediately before dispatch and aborts when the run list changed. No per-PR or arbitrary SHA is accepted. A qualifying gap results in exactly one `workflow_dispatch` of `.github/workflows/owner-hp-seeded-2p-research.yml` on `main` through the owner's existing `gh` login. GitHub's own research workflow concurrency remains in force.

This is **fallback dispatch**, not an additional fixed-volume research schedule. It cannot guarantee that a late GH cron trigger will not arrive immediately *after* the final census; that race remains bounded by GitHub's same-workflow queue/concurrency group. The 90-minute gap deliberately favors a genuine delayed schedule and priority HP builds over maximal CPU duty cycle. It also intentionally does not autonomously recover a persistent same-source science failure or claim release credit. An hourly agent may separately inspect a stopped run and fix the root cause.

## Evidence and acceptance

Read `%LOCALAPPDATA%\UR-Recomp\HPResearchFallback\last-status.json` for an exact source SHA, latest run ID and whether the check actually dispatched. The script never emits raw CLI errors or credentials. Run `py -3 hp_research_fallback.py --dry-run` for a non-dispatch census, using the script from the installed directory. Exit code 2 fails closed and writes a bounded status. The script runs no game code itself; after GitHub completes, **audit the resulting Windows artifact** with `python -m tools.hp_science_archive_audit` and separately fetched run API JSON. A successful CLI API dispatch is *not* a successful run, and neither counts as original/native parity or release acceptance.

**Validation:** Synthetic `tests/unit/test_hp_research_fallback.py` covers cooldown, active jobs, main ref, failure lockout, API malformation, delayed schedule race, local mutex and dry run. Python logic can be exercised on Linux without installing or dispatching a Windows task. **Windows installer/task execution and real HP behavior require the owner to run the package**, so neither can be declared tested by a hosted Python unit pass.
