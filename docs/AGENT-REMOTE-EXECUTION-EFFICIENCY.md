# Shared-agent remote execution and Desktop Commander efficiency

**Operating rule:** preserve the five interchangeable hourly agents (:00, :12, :24, :36, :48), the ranked work board, source-integrity checks, independent qualification and all final-head CI requirements. Reduce **transport calls per useful result**, never by skipping evidence, cutting tests, suppressing errors or denying necessary access to the owner's Windows PC. This policy refines tool routing; it does not create a separate lane, agent, lease or approval authority.

## Route each operation to the least costly suitable tool

1. **Repository metadata and publication:** use the GitHub connector directly for current main identity, files, PR/issue discovery, comments, exact heads, status checks, Actions runs, source blobs, atomic tree commits and supported workflow dispatches. Do not open Desktop Commander just to run `gh`, `git status`, `cat`, `curl` or GitHub API reads that the connector can safely perform.
2. **Execution that does not require the owner's PC:** use the available local execution environment or qualified GitHub Actions on frozen source. Never call a platform unavailable in that dispatch just to comply with habitual tool preference.
3. **Windows-only execution or data:** use Desktop Commander for real local programs, protected owner-only hardware, Windows build or installation tests, original/native observations, or when a **real executable task** can only be completed on the authorized PC. Do not withhold PC access from a qualified task to meet an arbitrary quota.
4. **No executable Git checkout:** a DNS failure in the current agent environment does not establish that GitHub itself is unreachable. Read the exact public/current GitHub source and relevant PRs through the GitHub connector; continue applicable review, reconciliation, scoped source edits with proper preflight, and hosted tests. For operations that genuinely require execution, select a supported local environment, authorized PC, or existing CI. If none is available, report the exact unverified action once in the owning handoff when new and choose other actionable work. Never pretend that connector data executed the offline selector, local tests or an original/native witness. One bounded connection diagnosis per environment or changed condition is enough; do not keep retrying identical DNS failures inside one dispatch.
5. **No-op dispatch:** after evaluating the top five shared candidates (and farther if needed), a genuinely blocked run may stop with zero commits and **zero Desktop Commander calls**. Do not use the PC for a new status check, redundant agent onboarding, or to produce another unchanged blocker report. Inspect fresh live evidence where needed so transient recovery or a new useful task is not overlooked.

## Batch safely when the PC really is required

- **Plan one bounded work unit before calling.** A unit may include independent read-only inspections, related build steps, a small test suite and a final digest. Prefer one `start_process` invocation that runs the unit with explicit working directory, error handling, reasonable timeouts and exit-status propagation over many separate terminal launches. Use one `read_multiple_files` for related files when that is clearer than multiple file reads.
- **Separate dependent decisions.** Do not batch a destructive operation with its authorization, an unreviewed PR merge with its checks, or a source rewrite with a test whose result must change the implementation choice. Stop on failure; preserve command, exit code, environment and source SHA. Maintain worktree isolation and check live conflicting writes before edits.
- **Let long processes work.** Use the process tool's built-in synchronous wait where appropriate. For longer commands, send output to a bounded local log plus a short machine-readable result/receipt. Read after a meaningful completion condition instead of polling `read_process_output` every 1–3 seconds. Never rerun a timed-out mutation without first checking whether it completed.
- **Return a short result:** observed source/head, steps run, exit codes, tests passed/failed, paths and SHA-256 of meaningful artifacts, remaining failures and next action. An existing PR or handoff owns this receipt. Do not upload secrets, ROMs, private paths or raw logs unnecessarily. Keep required independent source/artifact provenance.
- **Always retain the escape hatch.** If batching obscures a failure, overwhelms bounded output, interferes with interactive debugging, or requires a mid-step judgment, use the separate calls necessary to diagnose it. The correct metric is evidence-bearing work per call, not minimum calls at any cost.

## No redundant remote activity

- Freshly verify live PR heads, collisions and acceptance-relevant CI before consequential changes or merges. Reuse immutable source/document context within a dispatch; do not re-fetch unchanged large files for each minor question.
- Prefer a complete atomic Git tree/commit for one coherent change over one remote file write or push per file. Do not skip no-overwrite protection or review head leases.
- Launch relevant CI once on a stable exact head, reuse valid existing receipts, and reconcile when results become available. Avoid rapid polling of unchanged Actions runs, redundant dispatches, draft/ready toggles or forced pushes just to restart a check.
- The existing qualification ledger, QA01 original/native requirements, WIDE-07 authentic moving-course evidence, Windows physical testing and human-made 3D model hold all remain unchanged.

## Measure outcomes, not mere activity

The November 11 Desktop Commander local historical snapshot reported **10,019** calls across **53** sessions and eight recorded days; **6,807** were `start_process` and **1,764** `read_process_output` (8,571 combined, about 85.5%). The latest 1,000 retained calls are a mixed-project, truncated device-local sample and do **not** prove how many calls each UR agent made, what Desktop Commander bills, or whether the current five agents use the PC. Treat these figures as an initial directional baseline, not a target, price or per-project attribution.

For future comparable windows, record the plugin's actual total and by-tool deltas, calls attributable to the shared pool where auditable, useful completed tasks, independent qualified merges, and authentic product/evidence changes. Report any unverifiable split as **not measured**. Compare completed result per tool call **and** total game-progress results; do not claim success if calls fall only because agents stop doing useful work. No recurring new monitoring workflow or dedicated bookkeeping agent is authorized.
