# Owner HP missed-schedule research fallback (opt-in)

**Problem, November 1 2026 UTC:** GitHub's normal `schedule` delivery for the HP hourly research workflow has not been reliably observed since October 31 21:36 UTC. An eight-worker `workflow_dispatch` run completed successfully, so the runner and research code are known to work when GitHub *does* dispatch. GitHub cron is retained, not duplicated or disabled.

## Install (owner action only)

On the owner's **Windows x64 HP PC**, download the five-file [owner installer ZIP](../tools/ci/HP-Research-Fallback-Owner-Install.zip) (four scripts plus this README). Extract it to a normal local directory, then **double-click `Install-HP-Research-Fallback.cmd`**. This checks `py.exe` (Python 3) and `gh.exe` with an existing authenticated GitHub login; it never downloads a dependency, asks for a new GitHub token, uploads files or dispatches an initial run. If a prerequisite is missing, the installer reports an error rather than weakening the model. The ZIP's regression test verifies that every packaged file is byte-identical to the corresponding reviewed repository source.

The installed Windows Task Scheduler task runs under **the owner's current logged-in user** every 15 minutes. This choice avoids a stored Windows password and shares the already-authenticated `gh` credential store. A locked screen is fine; a fully logged-out session is **not** supported. The task never grants elevated rights and never executes repository code locally. Remove the task by double-clicking `Uninstall-HP-Research-Fallback.cmd`, or through Task Scheduler. The local script and last diagnostic remain under `%LOCALAPPDATA%\UR-Recomp\HPResearchFallback`; deleting them is optional after uninstall. Installing a newer package replaces the same named task, not a second timer.

## Dispatch algorithm

Each check uses `gh api` to read **the latest 30 runs for the specific research workflow**, the two other owner HP workflows, and exact current `main` SHA. It refuses to dispatch when: any research run is queued/active; an owner HP main build or benchmark is queued/active; latest research run started less than **60 minutes** ago (manual or schedule); latest run failed/cancelled on the **same main SHA** (stop retrying an unresolved source defect); the API response is missing/malformed/unauthorized; or a second process already holds the local lock. It performs second censuses of **research and both priority HP workflows** immediately before dispatch and aborts when any run changes, including a same-ID rerun's status, or a priority job becomes active. It then re-reads the exact `main` ref and refuses dispatch if it changed since the initial source-bound decision. All shared-status writes, including error reports, occur only under the acquired Windows process lock; a losing timer never overwrites its winner's result. If GitHub accepted a dispatch but the local receipt could not be persisted, stdout explicitly reports **dispatch accepted; inspect Actions before retry** rather than falsely asserting no dispatch. No per-PR or arbitrary SHA is accepted. A qualifying gap results in exactly one `workflow_dispatch` of `.github/workflows/owner-hp-seeded-2p-research.yml` on `main` through the owner's existing `gh` login. GitHub's own research workflow concurrency remains in force.

This is **fallback dispatch**, not an additional fixed-volume research schedule. It cannot guarantee that a late GH cron trigger will not arrive immediately *after* the final census; that race remains bounded by GitHub's same-workflow queue/concurrency group. Nor can it atomically pin `workflow_dispatch ref=main` against a branch update after the final ref read; the resulting Actions run's own `head_sha` and audited executable, not the pre-dispatch local receipt, establish the source that actually executed. The **60-minute pilot** was introduced after the physical HP completed a separate successful genuine cron research run and an additional recovered `workflow_dispatch` run on November 2, both with eight accepted seeds/32 real Windows guest processes and 9–10-minute total HP jobs. The previous 90-minute gap frequently left more than an hour of idle HP time during missed cron periods. With the same 15-minute task checks, a 60-minute window can raise the fallback-only theoretical upper bound from 8 cases/90 minutes to 8 cases/60 minutes (+50%), **only when actual cron remains missing and priority builds are idle**. Those maxima are not observed production throughput or a release-quality gain. The owner-only PR-comment dispatcher retains its separately implemented 90-minute guard. Keep a 360-second research horizon, main-branch identity checks, all same-source failure lockouts, re-read fences and HP Windows main-build/benchmark priority. Return the fallback to 90 minutes if a reproducible owner HP main-build delay greater than 10 minutes is attributable to the added fallback occupancy, if research starts overlap unexpectedly, or if the recovered cases per HP busy hour decline materially. The script does not reconfigure a task by itself; the owner must reinstall the reviewed five-file ZIP to activate this pilot. It also intentionally does not autonomously recover a persistent same-source science failure or claim release credit. An hourly agent may separately inspect a stopped run and fix the root cause.

## Evidence and acceptance

Read `%LOCALAPPDATA%\UR-Recomp\HPResearchFallback\last-status.json` for an exact source SHA, latest run ID and whether the check actually dispatched. The script never emits raw CLI errors or credentials. Run `py -3 hp_research_fallback.py --dry-run` for a non-dispatch census, using the script from the installed directory. Exit code 2 fails closed and writes a bounded status when persistence is available. The script runs no game code itself; after GitHub completes, **audit the resulting Windows artifact** with `python -m tools.hp_science_archive_audit` and separately fetched run API JSON. A successful CLI API dispatch is *not* a successful run, and neither counts as original/native parity or release acceptance.

**Validation:** Synthetic `tests/unit/test_hp_research_fallback.py` covers cooldown, active jobs, main ref, failure lockout, API malformation, delayed schedule and same-ID rerun races, local mutex, receipt failure after accepted dispatch, owner ZIP source identity and dry run. Python logic can be exercised on Linux without installing or dispatching a Windows task. **Windows installer/task execution and real HP behavior require the owner to run the package**, so neither can be declared tested by a hosted Python unit pass.
