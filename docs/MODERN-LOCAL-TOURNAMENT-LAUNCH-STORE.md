# Local Tournament launch checkpoint: atomic host-store seam

Status: this checkpoint store is integrated with the current player-facing Local Tournament coordinator and Windows product route, with focused filesystem tests. The previous standalone-only statement is historical. Whole-session/cross-process recovery remains QA-02 work.

The future live tournament host must save an attempt-scoped launch checkpoint **before** entering the original guest 2P route. The checkpoint's exact canonical `UR-LOCAL-TOURNAMENT-LAUNCH/1` bytes contain the active tournament ID, live attempt ID, selected fixture index/round/course/profile identities and the full immutable roster/schedule digest. The checksum detects accidental corruption; it is **not** an authorization signature.

`native/product/local_tournament_fixture_launch_store.{hpp,cpp}` reuses the repository's existing host state persistence pattern:

- One explicit host-provided path under an existing per-user data root. This layer does not choose a filesystem location, create an independent root or scan saved match history.
- Validate/encode first, reserve an independent same-directory `.pending-urlaunch-*` staging directory, check complete write/flush/close and atomically replace the destination. Windows retains replace/write-through via `MoveFileExW`; POSIX retains `rename`. Writers cannot truncate each other's staged bytes, and interrupted staging is ignored. A rejected candidate never overwrites the prior checkpoint.
- Read a maximum of **2,048 bytes** and distinguish missing, rejected/corrupt and I/O-error status. Decode must be canonical and the embedded tournament ID, selected unfinished fixture, participant identities and full schedule fingerprint must match the current authoritative tournament state before returning a pending attempt.
- Idempotent explicit retirement through the owning lifecycle, **only for the exact previously published checkpoint**, even after the fixture becomes completed. This deliberately differs from *restore*, which only admits unfinished fixtures. A sequential stale cancellation is rejected when its read-back attempt differs, and corrupt files cannot be silently retired as though they were an authorized launch. **The read/compare/remove sequence is NOT atomic across separate processes:** a new checkpoint published between the check and `remove` could still be deleted by an obsolete writer. QA-02 must close that race with a cross-process coordinator/lock or another evidence-backed conditional deletion mechanism. No result is generated by loading or deleting a checkpoint.

The caller must still serialize lifecycle decisions across processes sharing one checkpoint path; isolated staging avoids temporary-file byte corruption but does **not** provide compare-and-swap, prevent lost updates, or make stale retirement safe. The host must choose the existing account/profile-specific root, mint the instance/attempt IDs securely and coordinate checkpoint publication, stock route entry, completed paired run+match commit and fixture receipt persistence. A standalone successful save is **not** proof that a guest race occurred or that a tournament is playable. Process restore of an unfinished guest race is not claimed; a host that cannot safely resume it must explicitly cancel/retire the attempt.

Strict test coverage uses a real temporary filesystem: save → verify exact bytes → fresh-load, wrong instance/other entrant/other fixture/finished fixture rejections, invalid replacement preserving previous bytes, corrupt/truncated/oversized containment, repair, empty paths, missing directory, and clean idempotent retirement. It runs within the existing focused local-multiplayer contract workflow and tooling-unit suite. No new heavyweight native-boot workflow is introduced.
