The nonconstant difference between nominal CPU-clock conversion and actual SPC execution is source-explainable, **not yet a parity correction**: Snes9x `S9xAPUExecute()` reduces `SNES::smp.clock` by the nominal budget then calls `SNES::smp.enter()`; pinned `SMP::enter()` invokes `op_step()` **while** clock is negative, and `op_step()` executes an SPC instruction's per-bus accesses and ticks. Therefore the CPU-visible write can occur after a variable number of actually executed SPC bus cycles. The same `op_step` interpreter and opcode boundary influence the first IPL `78 CC F4` compare. This is a **plausible mechanistic explanation for integer counter overshoot**, not proof that all 3 first-write extra ticks are exclusively one instruction or exactly where native scheduling should change. A finer debt/opcode-cycle trace would be required.

Native first CPU CC is at `g_cpu.master_cycles=2164383306`, frame `6056`, `g_apu_frame_start_master=2164170140` (offset **213166** master cycles), extended frame clock **enabled**, mapped guest SPC cycle `103322545`, actual stored APU queue target `103322545`, native SPC queue scheduled age `103322463`, and consumed **on target** at `103322545`. Its subsequent first six CC writes occur exactly **98 CPU master cycles apart**, with guest target ages `103322550, 103322555, 103322559, 103322564, 103322569, 103322573`. In the original Snes9x source, **nine** CC writes are observed in this handshake interval versus **seven** native writes before native echo is observed; that is a consequence of the faster native SPC first read/echo loop, **not** proof of a 65816 instruction-level timing correction. Both CPUs first observe the echoed CC **four local SPC cycles after SPC echo**, so later CPU output-port reading is not the observed discrepancy.
