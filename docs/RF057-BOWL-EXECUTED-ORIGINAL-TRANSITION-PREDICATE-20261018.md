## Independently verified pinned generated-code branch anatomy (static, not executed evidence)

Read the actual pinned native generated USA code `gamesbyian/uniracers-recomp@10b864b9d14a7b7416dd909eb7b054c88faef101` rather than relying only on imported textual labels. `src/gen/bank80_part08_v2.c` includes the real `Input_WaitAnyButton` generated function containing `L_C1F5_M1X0`, `L_C1FE_M1X0`, `L_C205_M1X0`, `L_C20F_M0X0`, `L_C21B_M1X0` and `L_C225_M0X0`. In this **static source** the function calls `WaitVBlank`, invokes `Input_ReadPads`, and checks a 16-bit `cpu_read16_paced` at DP `$0072` then `$0074`. When a pad is held it calls a **further `WaitVBlank` around C20F–C214** and reads the held pad words again before eventually returning. The same pinned generated `src/gen/bank80_part0a_v2.c` `Input_ReadPads` contains *real* `cpu_read16_paced(…0x4218)` and `(…0x421a)` followed by stores to DP `0072/0074`. This gives a concrete observed-code lineage for a possible confirmation/wait mechanism, and explains why *one identical supplied controller event stream* need not imply immediate identical observed scene entry. **It does not demonstrate the function executed on the Bowl handoff in either guest**, does not establish an original↔native 65816 PC/CPU master epoch, and does not prove the exact two-frame lag is caused by this wait. The live source trace is explicitly capable of recording C1F5..C23B, D1DB..D1F9 and all immediate branch status flags.
